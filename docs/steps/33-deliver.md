# I3 · ESLint、README、report 收口

**做什么**：把「别人能接手」这件事做完 —— 规则锁死、文档说清怎么跑、验收结果写成报告。

**依赖**：全部

**预计**：1 小时

---

## 三件事，缺一件都不算交付

| 件 | 缺了会怎样 |
|---|---|
| ESLint 规则 | 下一个人 `npm run lint` 通过，但他不知道哪些规则是**刻意**开的 |
| README | 拿到仓库的人不知道跑起来的顺序（`setup` 必须在 `dev` 之前） |
| report | 「做完了」只是口头承诺，没有可核对的验收记录 |

---

## 1. ESLint：把「刻意的」写进注释

现有配置里已经有几条不是默认的项目规则（分层约束、禁 `any`）。要做的：

- 每条**非默认**规则上方加一行注释，说明它防的是什么
- `eslint .` 必须在**全仓**通过，不只是 `src/`

**不要**为了过 lint 加 `eslint-disable`。任何一处 `disable` 都要在 README 的
「已知例外」里列出理由，否则下一个人会照着加第二个。

---

## 2. README：给第一次拿到仓库的人

只要六节，多一节都是负担：

```markdown
# 片段标注工作量统计

## 这是什么
一句话 + 一张截图（可后补）

## 跑起来
node 版本、npm install、node scripts/setup.mjs --reset、npm run dev、账号

## 四个角色能做什么
管理员 / 标注员 各能做什么（表格）

## 核心数据模型
四张表的职责与关系（账本是唯一数据源这一条必须写）

## 验收怎么跑
npm test（707 例）、node scripts/e2e-check.mjs（53 项）、
npm run invariant:check（不变量）

## 已知限制
指向 docs/steps/00-INDEX.md 的「未修的已知项」表，并写出 4 条需要人工目视的
```

**「跑起来」那一节必须写明顺序**：`setup --reset` 会建库与种子，
不跑它 `dev` 起来的页面全是空的，而这个错误新人一定会犯一次。

## 3. report：验收记录

`docs/REPORT.md`，结构固定：

```markdown
# 验收报告

## 结论
一句话：能交付 / 不能交付 + 依据

## 交付范围
30 个功能点（A1–H2）+ 计划外 E8a，逐组一行

## 自动化验收
| 层 | 数量 | 结果 |
| 单元测试 | 707 | 全绿 |
| 全链路 | 53 | 全过 |
| 不变量 | 5 组 | 0 违反 |
| 静态检查 | audit:rules / audit:sql / eslint / tsc | 全过 |

## 变异验证汇总
每个功能点至少一次，列出「改坏了什么 → 哪个用例变红」
（这张表是「测试真的在测东西」的唯一证据）

## 人工验收清单
4 条必须人眼看的，写明「验了什么、看到什么」

## 未修项
指向 INDEX 的表，不重复抄

## 已知风险
3 条以内，按严重度排
```

### report 最容易写成「自我表扬」

反例：

> ✅ 所有测试通过，功能完整，代码质量高。

正例：

> 707 例通过。但其中「撤销方向」这条**无法被任何用例覆盖**（Workbench 里调用点传
> `before` 还是 `after`，实测改错后 510 例全绿），只能人工验：拖一段 → Ctrl+Z →
> 必须回到原位。

**报告的价值在于写出「哪里还不可靠」，不在于复述测试有多少个。**

## 验收

- [ ] `npx eslint .` 全仓通过
- [ ] README 里的命令**逐条照着跑一遍**，每一步都能成功
      （尤其 `setup --reset` → `dev` → 登录 → 看到任务）
- [ ] REPORT 里的数字与实际一致（707 / 53 / 5 组）
- [ ] REPORT 的「人工验收清单」不是空的
- [ ] REPORT 的「已知风险」至少有一条真实的（没有风险是可疑的）

---

## 易错点

| 陷阱 | 后果 |
|---|---|
| README 里的命令自己没跑过 | 新人第一步就卡住 |
| report 只写通过项 | 掩盖了真实的不确定性 |
| 用 `eslint-disable` 换绿灯 | 下一个人照抄 |
| 数字从旧报告抄 | 707 变成 510 也没人发现 |
